# 性能

> ⚠️ **写入数字强依赖平台的落盘语义**。引用时请一并说明平台。
> 数据为 3 轮取中位数;Linux 数据来自共享 CI runner,仅作指示性参考。

## 读取

| 场景(10 万文档) | macOS (Apple Silicon) |
|---|---|
| `find` 全量扫描 | ~8 µs/条 |
| 按 `_id` 读 | 亚毫秒 |
| `find_page` 排序+分页(内存增量) | ~12 MiB @100k |

## 写入

| 场景(1 万文档) | macOS | Linux |
|---|---|---|
| 逐条插入(每条一个事务) | ~185 条/秒 | ~1,400 条/秒 |
| `insert_many` 批量 | ~44,000 条/秒 | ~300,000 条/秒 |

### 为什么逐条插入这么慢 {#why-slow-write}

**这不是实现缺陷,是 fsync 的物理成本。**

Rust std 在 macOS 把 `sync_all` 映射到 `F_FULLFSYNC`(强制磁盘写缓存落物理介质),实测比 POSIX `fsync` 慢 **66 倍**;Linux 映射到 `fdatasync`,无放大。

而且 fsync 成本随文件增大而恶化(3.87 ms @1k → 30.2 ms @10k),所以逐条写入会**越写越慢**。

**结论:要吞吐就用 `insert_many`**,把 N 次提交合并成 1 次。

## 索引

| 查询场景 | 全表扫 | 走索引 | 加速比 |
|---|---|---|---|
| 唯一字段等值(命中 1 条) | ~510 ms | ~1 ms | 300–4000x |
| 范围(命中 1%) | ~425 ms | ~8 ms | ~55x |
| 复合(前缀等值+后缀范围) | ~410 ms | ~22 ms | ~19x |
| 低选择率等值(命中 10%) | ~430 ms | ~76 ms | ~5.7x |

| 项 | 数值 |
|---|---|
| 建索引回填 10 万条 | 1.2–2.5 s |
| 每多一个索引 | +80% 写入成本 |

## 内存

- `find` / `count` / `update` / `delete` 全部**流式处理**,内存 O(命中数) 而非 O(集合大小);
- 排序分页用 `find_page`(两遍法):先收集「排序键 + `_id`」排序,再按主键回取页内文档;
- 游标(`scan()`)持有读事务,`next_batch(n)` 从上次位置续取,内存 O(一批);
- 旧接口 `scan()` 会全量物化,已标注 deprecated,仅限小集合。

## 基准命令

```bash
cargo run --release --example bench -- 10000 100000    # 读路径与内存
cargo run --release --example bench_write -- 10000 3   # 写路径归因
cargo run --release --example bench_index -- 100000    # 索引效果
```

## 持久化

每次写事务提交都会落盘(redb 默认 `Durability::Immediate`)。

**不提供**关闭落盘的选项 —— 防止静默丢数据。需要吞吐时用批量写入把 N 次提交合并为 1 次。
